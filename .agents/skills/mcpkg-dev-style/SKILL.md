# Missdrop 的开发习惯

开始前读目标仓库的协作说明和 CONTRIBUTING.md（如有），再看相邻实现、对应测试和近期提交。下面是跨项目的默认偏好。用户本次的具体要求优先；运行环境、分支保护、构建命令和交付格式由当前项目决定。仓库说明与实际配置有出入时，指出具体矛盾；以当前代码核对旧记录，只在影响交付的取舍上请用户确认。

## 架构与目录

- 开发前先想好架构。新项目先列一棵简短的目录树，标出程序入口、主要模块和对应测试。用一条实际用例串起调用顺序，讲清哪个对象保存状态、哪个对象执行规则、结果返回给谁，再开始写实现。已有项目先沿入口找到本次改动所属的模块，只规划受影响的部分。
- 目录按职责命名。源码放在语言或仓库约定的代码目录，相关类按业务功能归在一起；同一功能有多种实现时，把它们放在同一模块下。小项目用几个命名清楚的文件就能表达关系时，保持平铺。
- 测试按被测功能组织，让人从源码能直接找到对应测试。测试专用的输入样例跟随测试存放。文档和构建脚本各有明确位置，仓库根目录保留常用入口和项目配置。

## 代码

- 把操作放在持有相关数据的对象上。调用方负责决定下一步，接收方负责检查自己的状态。几个入口仅默认参数不同时，让它们补齐参数后调用同一实现。简单查询可以直接返回；相关小类可以同文件，独立脚本可以直接写。
- 类名用目标项目已有的名词，方法用能说清动作的动词。名称长短取决于作用域：在一个小集合类里，push、sample 已足够；同时处理当前值、下一步的值和一批值时，在名称中明确区分。返回多个值时，先分别命名，再按接口顺序返回。
- 空行留在步骤之间。连续给同一对象赋值可以紧挨着写，从读取切换到校验、从构造结果切换到更新状态时空一行。先处理无效输入和提前返回，让正常路径从上往下读。几行相似代码如果分别对应不同含义的字段，可以保留平行写法，别为了缩短代码把含义藏进索引。
- 入口读取配置、接收输入并调用负责执行的对象。界面需要提前提示输入错误时，复用执行路径上的校验，避免两个入口对同一输入给出不同结果。只依赖参数的简单转换可以直接写成函数。
- 在可能失败的操作附近处理错误，区分用户能采取不同措施的情况。提示里写清哪一步失败；如果检查某项配置或输入就能解决，写出它的实际名称。带单位的常量把单位写进名字。
- 代码中禁止出现中文。源码、测试和脚本中的标识符、注释、docstring、字符串、日志及错误提示一律用英文。项目需要中文界面时，将译文放在独立的本地化资源中。把短注释放在相关语句前，交代从代码看不出的原因，如为什么提前分配空间、比较时谁应排在前面。简单委托和直接返回无需逐行解释。文档沿用目标项目的语言。
- 写 Python 领域类时，优先用普通类和显式 `__init__` 说明初始化关系。为接口补齐必要类型标注，沿用仓库配置的格式化、静态检查和类型检查工具。多行说明性 docstring 的开头和结尾三引号各自独立成行；复杂方法交代参数含义、返回结构和异常条件。
- 每完成一个行为，同时判断现有测试是否足够。正常流程、边界、异常或修复过的缺陷需要验证时，当场更新相应测试。使用仓库已有框架，测试真实可观察的结果。新增黑盒测试暴露缺陷时，先按需求判定预期行为，再修正实现或错误的测试断言。若验收对象是打包程序、CLI 或交互流程，还要通过真实入口在目标环境验证。区分通过、跳过和未验证的范围。

## Git 与协作

- 先看当前分支、工作区和暂存区，保护已有修改。按独立、可验证的小功能提交，相应实现和测试放在一起。粒度可以小到一个函数，无需等整个模块写完。验证通过后再提交，暂存时只选本次相关文件和改动块，交付时附简短提交说明和提交号。
- 提交标题通常用“英文小写动词 + 具体改动对象”。新增用 add，调整既有行为用 change 或 update，删除用 remove，单纯排版可写 format code。修复尽量点出触发条件；一次边界测试也可以单独提交。改动跨几个文件但共同验证一条规则时，放在同一提交。通常不加类型前缀；目标仓库已有统一格式时从其约定。
- 用户说“先给我看”“别 commit”或“只 review”时，在对应边界停下。多个视觉方案先放临时目录，让用户用同一段真实内容比较。仅获准本地提交时，不据此推送、发布审查或操作 PR。
- 沿用当前项目的开发分支和合并方式。获准在检查通过后合并时，确认检查对应最新提交；要求同步时核对本地及远端指向。直接推送、强制回退、bypass、共同署名等按本次授权和项目规则执行。优先使用项目已有的开发分支；同步当前分支、推送本地提交是两项操作，避免顺带切分支或把尚未发布的提交推到远端。
- 设计有疑问时先查需求、原始资料和已有实现。若仍有影响接口、用户行为或交付范围的选择，说明依据、推荐方案及代价，再请用户决定。具体任务要求逐项确认时，按小批次讨论。把硬性需求、参考实现、个人建议和已确认决定分清楚；若要偏离用户指定的参考方案，先说明原因和影响，再实现。

## 版本发布

- 配置自动发布时，在 main 已合入的目标提交上打版本标签。由推送版本标签触发 CI，检查和构建成功后创建 GitHub Release，有交付产物时附在该版本下。实际打标签和发布需有本次授权。
- 标签和 Release 标题使用同一个带小写 v 的版本号，例如 `v0.1.4`。正文用一行链接到上一发布版本与本次标签的比较，例如 `Full Changelog: [v0.1.3...v0.1.4](https://github.com/OWNER/REPO/compare/v0.1.3...v0.1.4)`。首次发布可省略这一行。

## 工具与交付

- 复用项目现有的构建入口、脚本和配置。入口保持简短，成段的脚本逻辑放在独立文件。工具输出让人一眼看出正在做什么、哪一步失败；按实际支持的平台验证。
- 临时下载、对照稿、生成物和本地协作笔记按用途放置。提交前检查文件清单，保留项目要求交付的成品；个人预览和明确仅供本地使用的文件放在忽略范围。新增文件不自动套个人版权或编辑器署名头，保留项目已有的许可和署名要求。

## 文档与审查

- 沟通默认用简洁中文，项目文档沿用目标文件的语言。开头直接说明读者关心的问题。给出实际命令、运行目录和预期结果，保留命令、参数与路径的拼写和大小写。
- README 开头用一两句交代程序做什么、使用者会得到什么。构建命令后紧跟产物位置；用法先给最短可运行例子，再列可选参数。已有成品可直接使用时，把直接使用和从头构建两条路径写开，只列影响复现的条件。贡献指南留给开发者，部署说明按读者实际拿到的文件验证命令。
- 面向最终用户的工具，按第一次实际使用的顺序写编号步骤，每步写一个操作。界面按钮和命令面板里的选项用粗体保留原名，配置键用行内代码。可选设置先交代适用条件；需要截图时紧跟对应步骤。最后一步让读者实际用一次。
- 报告先讲整体思路，再讲各部分为什么这样做。并列方案用同一组问题说明，例如各自按什么规则选择、条件相同时怎么处理、这个差别怎样影响结果。能用一个具体输入和观察到的输出说明的，就写例子。数字、截图和终端输出来自真实记录，来源就近标注。
- 编辑已有材料时保留作者的内容和语气，只改用户点明的范围。审查意见写明具体位置、问题对读者或使用者的影响和改法。审查要覆盖用语、事实和多余内容。用户指定评审原始提交时，按那个版本给意见；获准发布 GitHub review 时，能定位到改动行的问题发成行级评论，并正式提交 review。排版变化在最终导出物上验证。

## mcpkg 的 Rust 开发约定

- 从 src/main.rs 的命令入口跟到供应方解析、JAR 检查和服务器状态变更。网络和构建错误应带上包名或路径。用英文模块注释交代职责，在兼容旧锁文件、提交变更和处理依赖的位置说明原因。
- 保持示例通用。以 tmp/sample-server 的独立副本验证变更。覆盖禁用后升级、缺少硬依赖、旧锁文件读取和失败时保留原 JAR。
- 优化前用 release 二进制测实际命令。记录样本规模、测量次数和缓存条件，分别报告目录枚举、描述符读取和网络开销。限制并发，共享 HTTP 客户端，只按可验证的内容摘要复用下载。
- 使用 cargo fmt、cargo clippy 和 cargo test 验证改动。本 skill 随项目维护。
